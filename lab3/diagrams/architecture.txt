# Архітектура та логіка взаємодії демонстраційного стенду (University Student Portal)

## 1. Схема потоків даних та меж довіри (Trust Boundaries)

[Student Browser] 
       |  (1) HTTPS / HTTP :8080 (Login, GET /items?q=..., /health)
       v
=== Trust Boundary 1: Internet -> DMZ ===
       |
[Nginx Reverse Proxy :8080]
       |  (2) Internal HTTP :8000 (Проксіювання API-запитів, перевірка заголовків)
       v
=== Trust Boundary 2: DMZ -> Internal Network ===
       |
[FastAPI Backend Service :8000]  <--->  [Auth / JWT Module]
       |  (3) TCP / SQL :5432 (Читання/запис оцінок, пошукові запити)
       v
=== Trust Boundary 3: Application -> Data Layer ===
       |
[PostgreSQL Database :5432]

## 2. Логіка взаємодії між компонентами
1. Клієнт (студент або викладач) надсилає запит через браузер на вхідний вузол **Nginx** (порт `8080`), який знаходиться у буферній зоні **DMZ** і виконує роль зворотного проксі (Reverse Proxy).
2. **Nginx** фільтрує вхідний трафік і перенаправляє легітимні запити у закриту внутрішню мережу Docker (`lab3_default`) до бекенд-сервісу **FastAPI** (порт `8000`).
3. **FastAPI** перевіряє автентифікацію користувача, обробляє бізнес-логіку (пошук даних за параметром `q`, перегляд успішності) та формує запити до бази даних **PostgreSQL** (порт `5432`).
4. **PostgreSQL** зберігає облікові записи, хеші паролів та академічні дані у постійному томі (`pgdata`), доступному лише бекенд-сервісу.

## 3. Критичні активи системи (найвищий ризик компрометації)
* **База даних PostgreSQL (`Student DB`):** містить персональні дані студентів та оцінки (високий ризик порушення конфіденційності та цілісності).
* **Токени сесій та облікові дані (`Credentials / JWT`):** компрометація дозволяє зловмиснику отримати несанкціонований доступ від імені викладача або адміністратора.
* **Точка входу Nginx + FastAPI параметри запитів (`q=...`):** основний вектор для ін'єкцій (SQLi/XSS) та DoS-атак з зовнішньої мережі Internet.
